Niyam architecture

A modular monolith with one background worker. A question passes input checks, an orchestrator, retrieval and generation, then output checks. Every answer cites its source passages or is an explicit refusal.

Layered view

Arrows trace one question: UI, API, input checks, orchestrator, output checks and back out. The connection map further down shows every link. Phase tags (P1 to P12) match the build roadmap.

Answering a question

Weak evidence produces a refusal, and a draft answer that fails the grounding check is refused too. Nothing is guessed.

sequenceDiagram
  participant U as User via Streamlit
  participant A as FastAPI
  participant G as Guardrails
  participant O as LangGraph
  participant R as Retrieval
  participant L as Gemini
  U->>A: POST /v1/query with token and question
  A->>A: authenticate, rate limit, add request id
  A->>G: check input for PII and injection
  G-->>A: ok or redacted
  A->>O: run graph for the question
  O->>R: hybrid search, keyword and vector
  R-->>O: candidate passages
  O->>R: rerank candidates
  R-->>O: top passages
  alt evidence is weak
    O-->>A: refusal with reason
  else evidence is sufficient
    O->>L: answer using only these passages
    L-->>O: answer with citation ids
    O->>G: grounding check
    G-->>O: supported or unsupported
  end
  O-->>A: answer with citations, or refusal
  A-->>U: streamed response

Orchestration graph

The LangGraph state machine. Lookups go through retrieval and reranking. Comparison questions, such as what changed between two circulars, take the tool path.

flowchart TB
  start([Start]) --> guard["Input check"]
  guard -->|blocked| refuse["Refuse safely"]
  guard -->|ok| route["Route the question"]
  route -->|lookup| retrieve["Retrieve and rerank"]
  route -->|compare or changes| tools["Tool path: compare circulars"]
  retrieve --> enough{"Enough evidence?"}
  enough -->|no| refuse
  enough -->|yes| gen["Generate cited answer"]
  tools --> gen
  gen --> check["Grounding check"]
  check -->|supported| finish([Return answer])
  check -->|unsupported| refuse
  refuse --> finish

Ingestion

Runs in the background worker so uploads never slow down answers. Each document stores a content hash, so ingesting the same circular twice creates no duplicates, and each chunk records which embedding model produced its vector.

flowchart LR
  up["Upload or fetch circular PDF"] --> job["Create ingestion job"]
  job --> q[("Redis queue")]
  q --> w["Worker picks up job"]
  w --> parse["Parse with Docling, OCR fallback"]
  parse --> clean["Clean text and add metadata"]
  clean --> chunk["Chunk by structure"]
  chunk --> emb["Embed chunks"]
  emb --> store[("Postgres: documents and chunks")]
  store --> done["Mark job complete"]

Data model

Planned tables. Documents carry regulator, circular number, issue date and status (active, superseded or withdrawn), so answers can say whether a source is still current. Only redacted question text is stored.

Dependency rules

Imports point downward. A lower package never imports an upper one.

api → agents → retrieval · llm · guardrails → db → core
ingestion → llm · db → core
evals → agents · retrieval (public functions only)
  • Only llm, retrieval and agents import LangChain or LangGraph.
  • Only db talks to Postgres directly.
  • Only llm builds models, and it is the only place the API key is opened.
  • Model names and providers come from configuration, never from code.
